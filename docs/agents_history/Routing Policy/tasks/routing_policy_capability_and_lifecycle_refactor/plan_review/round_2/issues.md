# Round 2 Plan Review

The plan is directionally strong, but it is not yet sound enough to execute as written because two lifecycle and integrity gaps remain unresolved.

## Findings

1. Major: Step 3's provider-derived vendor validation conflicts with the plan's own dynamic-vendor lifecycle, so stale vendor rules become impossible to enable, disable, or resave.
The plan says vendor options and backend validation should come from the current provider-derived vendor set for the selected `api_type` (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:30`, `.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:91`), while also explicitly preserving vendor-scoped rules as dynamic filters that should not block later provider vendor changes (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:31`, `.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:118`). It then adds a quick enabled toggle implemented through the existing update contract (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:93`, `.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:177`). In the current codebase, provider vendor values are freely mutable on update (`internal/admin/handler_provider.go:525-526`). That combination means a once-valid vendor rule can become stale after a provider edit, and then even a lifecycle-only change like disable/enable will fail validation because the stored vendor is no longer in the live provider catalog. The plan needs an explicit policy for persisted-but-currently-unmatched vendor rules: either lifecycle-only updates must bypass vendor recertification, or validation must allow a rule to retain its stored vendor set unless the scope itself is being edited.

2. Major: The exact-provider integrity model protects deletes but not provider updates that remove the referenced API type.
The plan validates `target_provider_id` against the selected `api_type` during routing-policy CRUD/import (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:89-90`) and adds `409 Conflict` protection when that provider is deleted (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:107-110`). But the current provider update flow can rewrite a provider's `api_types` wholesale (`internal/admin/handler_provider.go:453-500`, `internal/store/sqlite_provider.go:109-167`). As written, an exact-provider rule can therefore survive while its target no longer supports the rule's `api_type`, leaving a direct reference intact syntactically but broken semantically. That undercuts the plan's objective that exact-provider references preserve integrity (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:11`) and turns such rules into permanent fail-closed traps. The plan needs symmetric enforcement on provider updates as well: either reject API-type removals that would invalidate exact-provider rules, or define a coordinated rewrite path inside the same transaction.

**Verdict: 2 major, 0 minor valid issues.**
