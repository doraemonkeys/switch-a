# Round 3 Plan Review

## Findings

1. Major: Step 4 still leaves routing-policy config-transfer identity implicit, so preview diffing and cross-environment import/upsert behavior are not deterministic.
The plan adds routing policies to export/import and preview/applied counts (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:116-121`, `.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:289-291`), but unlike providers and groups it never states how imported policies match existing rows. Routing policies only have a storage-local auto-increment primary key today (`internal/model/provider_state.go:117-127`), while the current admin payload exposes that local `id` plus timestamps (`internal/admin/handler_routing_policy.go:19-30`). Step 4 does say to extend config-transfer DTOs, but it still needs to explicitly key preview/apply on the native unique tuple `(api_type, model_match_type, model_match_value)` preserved in Step 1 (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:50`) and to omit storage-local fields. Without that, the plan leaves add/update classification and cross-environment routing-policy import semantics ambiguous.

2. Minor: The staged-import validation contract still does not say duplicate routing-policy keys inside the imported payload are rejected before preview/apply succeeds.
Step 4 requires a normalized imported catalog and validation before any writes (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:119-121`, `.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:291-292`), but the enumerated invalid cases only cover dangling references, invalid vendors, unsupported provider API types, and mixed exact-provider plus filter scope (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:120`). The plan preserves duplicate-key conflicts for CRUD (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:97`) and keeps the unique tuple reserved even while disabled (`.agents/tasks/routing_policy_capability_and_lifecycle_refactor/plan.md:50`), yet it never states whether two imported rules with the same tuple should fail validation or be collapsed during catalog normalization. That leaves dry-run/apply behavior for duplicate imported keys ambiguous.

**Verdict: 1 major, 1 minor valid issues.**
